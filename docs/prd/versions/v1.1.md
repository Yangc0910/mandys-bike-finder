# Mandy's Bike Finder Version 1.1 UX Polish PRD

Version: 1.1

Status: Approved for implementation planning

Date: 2026-06-10

Production baseline: `v1.0.0-app-store-release`

Integration branch: `release/v1.1-ui-polish`

## 1. Summary

Version 1.1 is a controlled post-launch polish release for the existing App Store product. It improves clarity, visual hierarchy, mobile interaction, launch quality, and App Store presentation while preserving the version 1.0 product model and technical boundaries.

The release does not add a new business model or major product surface. It makes the current `Profile`, `Evaluate`, `History`, and `Settings` experience easier to understand and more trustworthy.

## 2. User Problem

Version 1.0 provides the required decision-support workflow, but the experience can still feel information-dense and visually inconsistent. First-time users may need more help understanding:

- Why a child profile is needed.
- Which listing input method to choose.
- When AI is used and what remains local.
- Which listing fields should be reviewed before analysis.
- How to interpret fit, deal, and risk guidance.
- What action to take after receiving a recommendation.
- What is saved locally and how to remove it.

Version 1.1 should reduce this cognitive load without hiding important limitations or adding unsupported capabilities.

## 3. Target Outcome

After the update, a parent should be able to:

1. Understand the app's purpose within the first screen.
2. Create or confirm a child profile without unnecessary uncertainty.
3. Select an appropriate listing input method.
4. Understand that AI is optional, explicit, and editable.
5. Review listing details before analysis.
6. Understand the recommendation and next action at a glance.
7. Save useful decisions and find them later.
8. Understand and control local data.

## 4. Success Criteria

Version 1.1 is successful when:

- The primary action on each screen is visually unambiguous.
- Required and optional information are consistently distinguished.
- Core actions have clear loading, disabled, success, and error states.
- Fit, deal, and risk are understandable without relying on color alone.
- Existing version 1.0 local data remains readable.
- No screen implies that AI, scraping, accounts, cloud sync, or payments are active when they are not.
- App Store screenshot states can be reproduced using the shipped UI.

No analytics dependency is required for release. Qualitative QA, App Store feedback, support questions, and later usage evidence may inform version 1.2.

## 5. Scope And Priority

### P0: Required For Version 1.1

- Define and apply a coherent visual system.
- Polish the app shell and bottom navigation.
- Improve Profile onboarding and saved-profile hierarchy.
- Clarify the Evaluate input, review, and analysis stages.
- Improve result hierarchy and next-step guidance.
- Improve History card hierarchy and empty state.
- Improve Settings grouping, trust copy, and local data controls.
- Improve web loading, offline, failure, and native launch continuity.
- Complete mobile regression testing and App Store screenshot source states.

### P1: Include If Low Risk

- Lightweight transitions that respect reduced-motion preferences.
- Consistent inline icons using existing or dependency-free assets.
- Copy-to-clipboard feedback for seller messages.
- Small contextual progress indicators in Evaluate.
- Visual emphasis for favorites in History.

### P2: Defer To Version 1.2 Or Later

- Comparison tools between saved bikes.
- History search, filters, or sorting controls.
- Cloud sync or multi-device state.
- New recommendation dimensions or scoring changes.
- New native plugins.
- Sharing, export, or notification workflows.

## 6. Product And Technical Guardrails

Every implementation task must preserve:

- One active child profile stored locally.
- Existing localStorage keys and compatible stored data shapes unless a migration is explicitly reviewed.
- Local/manual Evaluate fallback.
- Explicit user action before screenshot or text AI processing.
- Editable listing fields after extraction.
- Local History snapshots that do not re-fetch listings.
- Settings controls for profile, History, and all local data.
- `/privacy` and `/offline`.
- No OpenAI or LLM call on initial app load.
- Server-side-only provider keys.
- No marketplace scraping or login-gated automation.
- No account, payment, subscription, or paid feature surface.
- Separation between `www.mandysbikefinder.com` and `app.mandysbikefinder.com`.

## 7. Global Experience Requirements

### Visual Hierarchy

- Each screen has one page title and one concise supporting sentence.
- Each section has a clear purpose; avoid repeated eyebrow labels that add no meaning.
- Primary decision content is visually stronger than explanatory or destructive content.
- Body text remains readable on small iPhones and at increased text sizes.

### Actions

- Primary buttons use one consistent style and a minimum 44-point-equivalent touch target.
- Secondary and destructive actions are visually distinct from the primary action.
- Disabled buttons include nearby text explaining what is missing.
- Loading actions prevent duplicate submission and use action-specific labels.
- Success feedback confirms what changed and where data was saved.

### Forms

- Required and optional fields are labeled consistently.
- Validation appears near the affected field or action.
- Existing user input remains in place after recoverable errors.
- Keyboard, focus, and scrolling behavior must not hide the active field or primary action.
- Form controls must continue using at least 16-pixel input text to avoid iOS focus zoom.

### Empty, Loading, Error, And Offline States

- Empty states explain why the area is empty and provide one useful next action.
- Loading states describe the current operation, not merely "Loading."
- Error states explain whether local fallback is available and preserve entered data.
- Offline states distinguish local capabilities from network-required AI extraction.
- No state claims that AI works offline.

### Accessibility

- Do not communicate fit, deal, risk, selection, or errors through color alone.
- Interactive controls have accessible names and visible focus treatment.
- Touch targets are at least 44 by 44 CSS pixels where feasible.
- Motion is subtle and disabled or reduced under `prefers-reduced-motion`.
- Text and meaningful controls meet appropriate contrast expectations.

## 8. App Shell And Navigation

### User Problem

The shell works, but the bottom tabs and page headers can feel visually generic. Active state, iconography, and spacing should communicate a more deliberate app structure.

### Required Behavior

- Preserve four tabs: `Profile`, `Evaluate`, `History`, and `Settings`.
- Add a consistent icon for each tab while retaining text labels.
- Use more than color to communicate the active tab.
- Preserve tab state during normal tab switching.
- Scroll the newly selected screen to its expected starting position.
- Keep content clear of the home indicator and bottom navigation.
- Use one compact page-header pattern across all four screens.
- Avoid adding a new Home tab or hidden navigation drawer.

### States

- Active tab.
- Inactive tab.
- Pressed/focused tab.
- Offline banner present.
- Small iPhone safe-area layout.
- Large iPhone layout.
- Reduced-motion mode.

### Acceptance Criteria

- All tabs are reachable with one tap.
- Active tab is identifiable without color.
- Tab labels do not truncate at supported iPhone widths.
- No primary content or action is obscured by bottom navigation.
- Switching tabs does not trigger an AI or provider request.
- No heavy navigation or animation dependency is added.

## 9. Profile

### User Problem

First-time users need a clearer explanation of why Profile comes first. Returning users need the saved rider and recommended wheel size to be scannable without reading a dense card.

### Required Behavior

- Explain that height, age, and riding experience power fit guidance.
- Explain that the profile is stored on the device and requires no account.
- Separate required rider basics from optional preferences.
- Keep nickname optional.
- Preserve height and weight unit choices and normalization behavior.
- After save, show the child summary and recommended wheel size as the primary content.
- Show bike type, growth guidance, and fit caution as supporting content.
- Keep clear `Edit` and `Evaluate a bike` actions.
- Keep profile clearing available with confirmation.

### States

- First visit with no profile.
- Create profile form.
- Validation error.
- Saved profile.
- Edit existing profile.
- Clear confirmation.
- Profile cleared.
- Existing v1.0 stored profile loaded.

### Acceptance Criteria

- A first-time user can identify required fields before entering data.
- Saving still uses the existing local profile behavior.
- Existing v1.0 profiles load without manual migration.
- Recommendation logic and output meaning are unchanged.
- The recommended wheel size is visible without opening another section.
- Editing and canceling do not silently overwrite the saved profile.
- Clearing Profile does not clear History.

## 10. Evaluate

### User Problem

Evaluate combines several input paths, optional AI extraction, editable listing details, analysis, and result content. The user needs a stronger sense of sequence and a clear primary action at each stage.

### Required Flow

1. Confirm an active child profile.
2. Choose `Screenshot`, `Text or link`, or `Manual`.
3. Add listing information.
4. Review and edit listing details.
5. Run analysis.
6. Review result and next steps.
7. Save to History when useful.

### Input Selection

- Each input method includes a concise "best for" explanation.
- Screenshot remains the default method.
- Changing input method must not automatically send data or erase unrelated user input without warning.
- Link input remains reference/user-provided context and must not imply scraping.

### Screenshot

- Show a clear select/upload area.
- After selection, show preview, filename, replace, and remove controls.
- State that selection is local preview only.
- AI extraction starts only after an explicit button tap.
- Before AI extraction, explain that the screenshot may be sent for processing.
- During extraction, disable duplicate requests and show specific progress.
- After extraction, show editable fields and identify missing/uncertain information.
- On failure or limits, preserve the screenshot and allow manual entry/local analysis.

### Text Or Link

- Clearly separate listing reference URL from pasted listing text.
- Do not imply that every URL can be opened or read.
- AI text extraction, if shown, must be explicit and optional.
- Manual field review remains available.

### Manual

- Allow direct entry of the minimum useful listing details.
- Do not require every optional field before analysis.
- Explain which missing fields may reduce confidence.

### Review

- Review/edit is a visible stage, not hidden technical behavior.
- Core fields include title, price, brand/model, wheel size, bike type, condition/description, platform/location, and reference link when available.
- Extracted values are never presented as guaranteed facts.
- Editing a field after analysis invalidates the stale result and requires a deliberate rerun.

### States

- No Profile.
- Profile available, no listing.
- Input method selected.
- Screenshot preview only.
- AI disclosure before action.
- AI extracting.
- AI extraction success.
- AI extraction partial/fallback.
- AI unavailable or rate-limited.
- Review ready.
- Analysis disabled with reason.
- Local analysis running.
- Result ready.
- Inputs changed after result.

### Acceptance Criteria

- Initial Evaluate render does not trigger AI.
- Selecting a screenshot does not trigger AI.
- User can always review/edit fields before analysis.
- User can run local fallback when AI is unavailable.
- One dominant primary action is visible for the current stage.
- Missing Profile sends the user to Profile without losing avoidable listing input.
- Link behavior never claims unsupported marketplace access.
- Existing API routes and provider behavior are unchanged.

## 11. Result And Seller Message

### User Problem

The current result contains useful information but should make the decision and next action easier to scan.

### Required Behavior

- Lead with a plain-language overall recommendation.
- Include one concise explanation of why.
- Show `Fit`, `Deal`, and `Risk` in three consistent status blocks.
- Each status includes a text label and reasoning, not color alone.
- Include a `What to do next` section with practical inspect, ask, offer, or skip guidance.
- Present the seller message in a copy-ready card.
- Provide clear copy success/failure feedback when clipboard support is used.
- Keep `Save to History` visible and confirm successful save.
- Avoid numeric precision that is not supported by the product logic.
- Avoid language that implies safety inspection, certification, or a purchase guarantee.

### States

- Positive/green recommendation.
- Caution/yellow recommendation.
- Skip/red recommendation.
- Mixed fit/deal/risk statuses.
- Seller message present.
- Copy success or copy unavailable.
- Save success.
- Duplicate History save.
- Result invalidated by edited inputs.

### Acceptance Criteria

- Overall recommendation, fit, deal, and risk are understandable at a glance.
- A user can identify at least one practical next action.
- Seller message content remains based on existing local behavior.
- Save uses the existing local History format.
- Duplicate save behavior remains safe and understandable.
- No analysis or scoring semantics change as part of visual polish.

## 12. History

### User Problem

History should feel like a list of saved purchase decisions rather than a technical record of previous analyses.

### Required Behavior

- Empty state explains that saved evaluations appear here and links to Evaluate.
- Each card prioritizes recommendation, listing title, price, wheel size, child, and saved date.
- Source/platform and input method remain supporting information.
- Favorite/shortlist state is easy to identify and toggle.
- Details reveal the saved snapshot without re-running analysis.
- Delete requires an intentional action and confirmation.
- Opening History never calls AI or re-fetches a marketplace page.
- Preserve the current capacity of 10 recent saved evaluations.

### States

- Empty History.
- One saved evaluation.
- Multiple saved evaluations.
- Favorite and non-favorite cards.
- Expanded detail.
- Delete confirmation/cancel.
- Existing v1.0 saved records.

### Acceptance Criteria

- Existing saved records continue to render.
- Favorite changes persist locally.
- Deleting one item does not alter Profile or other History records.
- Empty state has one clear route to Evaluate.
- Detail content identifies that it is a saved snapshot.
- History remains usable offline for already stored data.

## 13. Settings And Privacy

### User Problem

Settings carries important trust information but should be easier to scan and less repetitive.

### Required Behavior

- Group content into `Privacy and AI`, `Local data`, `Support`, and `About`.
- Explain local Profile and History storage in plain language.
- Explain that AI is optional and starts only from explicit user action.
- Explain that provider keys remain server-side.
- Explain that marketplace content is user-provided and not automatically scraped.
- Show current local Profile and History counts.
- Keep separate clear Profile, clear History, and clear all controls.
- Visually separate destructive actions from informational settings.
- Keep the `/privacy` link.
- Show app name and current version.
- Retain practical fit/safety disclaimer.

### States

- No local data.
- Profile only.
- History only.
- Profile and History.
- Clear action confirmation.
- Clear success.
- No-op clear action.
- Offline access to local controls and disclosure.

### Acceptance Criteria

- Users can tell what data is stored locally.
- Users can tell when AI data may leave the device.
- Clear actions accurately describe their scope.
- Clear Profile does not clear History.
- Clear History does not clear Profile.
- Clear all removes both existing App Store local data sets.
- `/privacy` remains reachable.
- Settings does not expose provider credentials or technical diagnostics.

## 14. Loading, Launch, Offline, And Recovery

### User Problem

The transition from native launch screen to hosted app should feel intentional, and network failures should clearly distinguish local features from server-required features.

### Required Behavior

- Native launch and web loading visuals use aligned branding and background colors.
- The launch screen uses a static production mark and short product message.
- Any web animation is CSS-only, subtle, and non-blocking.
- No AI, provider call, font download, or heavy dependency is added solely for launch.
- Preserve `/offline`.
- Offline messaging states that saved Profile, History, and local guidance may remain available.
- Offline messaging states that AI extraction requires a connection.
- Slow or failed hosted-app loading offers an honest recovery path.

### States

- Native cold launch.
- Warm launch.
- Fast hosted-app load.
- Slow network.
- Offline before launch.
- Connection lost while app is open.
- Connection restored.
- Server action failure with local fallback.

### Acceptance Criteria

- No blank or misleading intermediate screen is intentionally introduced.
- Native and web visuals do not appear as unrelated brands.
- Initial launch does not call OpenAI or another LLM.
- Offline copy never claims AI availability.
- Local Profile and History remain accessible when already loaded and technically available.
- Cold, warm, slow, and offline launch paths are included in release QA.

## 15. App Store Screenshot Requirements

- Use real shipped UI as the screenshot source.
- Use fictional sample Profile and listing data.
- Do not show private seller information or real marketplace messages.
- Do not show accounts, payments, scraping, automation, or cloud sync.
- Prepare a coherent sequence covering value, Profile, Evaluate, Result, History, and optional Privacy.
- Prefer final captures from the iOS simulator.
- Marketing frames may add headline and background treatment but must not fabricate app controls or results.
- Use reproducible sample data so screenshots can be recaptured after minor UI changes.

## 16. Implementation Boundaries

Likely production files:

- `app/app/page.tsx`
- `app/app/globals.css`
- `app/app/offline/page.tsx`
- `app/public/launch-screen.svg`
- Approved iOS launch/splash assets

Implementation should not change API routes, provider interfaces, analysis logic, local storage keys, or Capacitor hosting strategy unless a separately reviewed defect requires it.

The large `page.tsx` may be split only through a dedicated, behavior-preserving task. Component extraction is not a prerequisite for visual polish.

## 18. Release Acceptance

Version 1.1 may merge to `main` only when:

- All P0 requirements are implemented or explicitly deferred with release approval.
- Lint and production build pass.
- Mobile regression passes with no P0/P1 blocker.
- Existing local Profile and History data remain compatible.
- Initial load and screenshot selection make no LLM call.
- Provider keys remain server-side.
- Preview deployment is reviewed before production.
- App Store screenshot source states are approved.
- Release notes and version labels are updated.
- Rollback to the version 1.0 baseline remains possible.

## 19. Explicit Non-Goals

Version 1.1 does not include:

- Account, login, or cloud sync.
- Subscription, payment, in-app purchase, or paid features.
- Marketplace scraping, automatic monitoring, or Bike Scout automation.
- New AI providers, major prompt changes, or scoring redesign.
- New recommendation dimensions.
- Native camera, notification, background-task, or database architecture.
- Large Capacitor or Next.js rewrite.
- Changes to the public web MVP.
